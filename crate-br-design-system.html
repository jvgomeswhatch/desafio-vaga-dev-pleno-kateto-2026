v1.0 / FOUNDATION

Design System para vender skins
como quem vende uma Karambit Doppler.

CRATE//BR é a vitrine brasileira de skins de Counter-Strike. Este documento é a fonte única de tokens, componentes e padrões para o produto inteiro — landing pública, autenticação e CRM interno de leads.

01 / Identidade

HUD-first

Estética de inventário Steam + HUD de jogo. Brackets, separadores //, dados em mono e a borda lateral de raridade como marca visual.

02 / Paleta

StatTrak Orange

#cf6a32 como cor de marca — específica do universo CS, não o verde ácido genérico. Raridades oficiais como sistema de cor.

03 / Signature

Float Meter

A barra de wear (0.00 → 1.00) é o elemento visual recorrente. Aparece em cards de skin, indicadores de raridade e progressões.

ENGINEERING / STRUCTURE

Arquitetura sugerida

Tokens centralizados em tokens.css. Componentes seguem Atomic Design (atoms → molecules → organisms → templates → pages). Stack indicativa: Next.js / React + CSS Modules ou Tailwind com preset dos tokens.

src/ ├── app/ # rotas (Next App Router) │ ├── (public)/ │ │ └── page.tsx # landing │ ├── (auth)/ │ │ └── login/page.tsx │ └── (internal)/ │ └── leads/page.tsx # kanban │ ├── styles/ │ ├── tokens.css # ÚNICA fonte de variáveis │ ├── reset.css │ └── globals.css │ ├── components/ │ ├── atoms/ # sem dependência │ │ ├── Button/ │ │ ├── Input/ │ │ ├── Badge/ │ │ ├── Avatar/ │ │ └── FloatMeter/ # signature │ ├── molecules/ # compõem atoms │ │ ├── FormField/ │ │ ├── SkinCard/ │ │ └── LeadCard/ │ ├── organisms/ # compõem molecules │ │ ├── LandingHeader/ │ │ ├── Hero/ │ │ ├── SkinShowcase/ │ │ ├── LeadForm/ │ │ └── KanbanBoard/ │ └── templates/ │ ├── PublicLayout/ │ └── InternalLayout/ │ ├── features/ # lógica de domínio │ ├── leads/ │ │ ├── lead.types.ts │ │ ├── lead.service.ts │ │ └── useLeads.ts │ ├── round-robin/ │ │ ├── sellers.ts # [M,R,N,P,L] │ │ └── assignNextSeller.ts │ └── auth/ │ └── useAuth.ts │ ├── lib/ │ ├── api.ts │ └── storage.ts │ └── types/ ├── skin.ts └── lead.ts
Round-robin entre sessões: persistir o índice do próximo vendedor em uma chave única — seller_pointer — no backend (ou em localStorage + sync se o teste for client-only). Operação de atribuição deve ser atômica: ler ponteiro → incrementar (mod 5) → gravar → retornar vendedor. Sob concorrência real, usar transação no banco ou lock otimista. Documentar a decisão.
ENGINEERING / RULES

Convenções

Regras curtas, não negociáveis.

Nomenclatura de componentes

// Arquivos & componentes
Componente em PascalCase · SkinCard.tsx
Hook em camelCase prefixado use · useLeads.ts
Constante em UPPER_SNAKE · SELLER_ROTATION
Tipo em PascalCase · type Lead = {}

// CSS / Classes (BEM relaxado)
Bloco · .skin-card
Elemento · .skin-card__visual
Modificador · .skin-card--featured
Estado · .is-loading · .is-dragging

// Tokens
Cor · --color-{escopo}-{nome} · ex: --color-rarity-covert
Espaço · --space-{n} · ex: --space-4
Type · --text-{tamanho} · ex: --text-xl

Regras de uso

  • 01 · Toda cor, tipografia, espaçamento e borda vem de token. Sem hex direto, sem px hardcoded em CSS de componente.
  • 02 · Mobile-first sempre. Media query é só min-width. Layout de coluna única é o default; grid/flex elaborado entra em breakpoints maiores.
  • 03 · Atomic Design rigoroso. Atom não importa molecule. Molecule não importa organism. Quebrar isso é dívida — registre.
  • 04 · Acessibilidade não é opcional. Focus ring visível, labels conectados a inputs, contraste mínimo AA, prefers-reduced-motion respeitado.
  • 05 · Round-robin do vendedor é responsabilidade de features/round-robin. Nenhuma view chama essa lógica direto — vai pelo service.
  • 06 · Telefone usa máscara (##) #####-####. Validação rejeita ausência de DDD.
